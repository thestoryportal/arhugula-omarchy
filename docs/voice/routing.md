# First safe command route

`VoiceRouter` consumes trusted Action definitions and a trusted VoiceState
supplier. Actions bind capability IDs, catalog versions, fixed arguments, aliases
and display labels. They are not generated by a model. VoiceState binds current
session context, focus/context epoch key, one-shot activation ID, mute and mode.
The adapter must update these from authoritative VM state. None of these Python
entrypoints is exposed to untrusted model tools or a network transport.
The router stamps every constructed command with `source=voice`, even when the
supplied generic session context says terminal/test. VM profile authorization
and all resulting observations/receipts therefore retain voice provenance.

Normalization covers Unicode compatibility, case, punctuation and whitespace.
Exact aliases are deterministic. An optional injected proposal function returns
only known capability IDs, catalog versions and finite confidence scores in a
closed shape. There is no provider process in this implementation. Without a
provider, lexical similarity ranks aliases; this is a fallback, not a trained
semantic model. Scores below 0.85 or top-two gaps below 0.15 require clarification
on a new activation. Every non-exact/model-inferred candidate is previewed even
at high confidence, preventing fuzzy matches from silently executing negations
or unrelated wording. Corrections always preview too.

Only VM ControlPlane can authorize. `request_confirmation(command, context_key)`
stores an immutable command and random token for 30 seconds. `confirm(token,
channel, context_key, approved=True)` is for trusted panel/keyboard/voice adapters
only, never a model-callable tool. Tokens are single-use and lost on restart;
expiry, context mismatch, unknown/replayed tokens and policy/catalog failures
cannot execute. The router binds the complete session context plus epoch key,
not merely a window name. Voice confirmation requires a fresh activation and
an exact yes/confirm/no/cancel answer. Panel/keyboard require boolean decisions.
The original preview binding is checked before interpreting an answer, including
before speaking clarification for an ambiguous voice answer.
Muted or noncommand state cannot execute or speak. Session activation history is
bounded at 4096 turns; pending previews are bounded at 128; exhaustion blocks
until the owner creates a fresh session, without forgetting replay protection.

Interaction is a new independently versioned kind (`kind: interaction`,
`version: 1`), structurally distinct from execution Event. It records preview,
confirmation and clarification observations in the same journal, with stable
IDs, context, phase and safe details. Unknown kinds/versions remain rejected.
Execution replay suppression uses execution Events only; a preview is not an
execution. No audio, transcript, raw provider errors or approval token is logged.
The `voice.preview` observation also imposes a durable approval requirement on
its command ID (stored as Interaction.interaction_id). Every dispatch rereads
that restriction under shared journal ownership. Another control plane or a
SQLite reopen cannot dispatch a safe correction/inferred candidate without an
approval token. Losing the token leaves the command ID fail-closed; preview
observations never grant approval or count as execution, and clarification
observations impose no execution restriction.

The router carries a trusted current-state guard into VM dispatch/confirmation.
It compares the full turn snapshot, including activation, context epoch, mute
and mode, after journal ownership/read and again after persisting execution
intent immediately before calling the executor. Guard failure or unavailable
state blocks with `context.stale`; an intent already recorded remains protected
against retry. Speech gets the equivalent check after its observation/preview
write immediately before the speech callable.

Actuation ownership is an adapter contract: the VM owner must use monotonically
changing context epochs (including transitions away and back), publish current
state synchronously, and serialize state transitions with the final guard and
actual executor/speech actuation using platform ownership or an atomic
compare-and-act mechanism where supported. Guard/state callbacks run under the
journal dispatch lock; owners must use a consistent lock order. The journal
lock serializes dispatchers, not desktop focus or mute changes. These Python
checks close waits inside authorization/persistence but cannot make a later
external platform operation atomic. No live speech adapter is installed here;
one must enforce this contract at its actual actuation boundary.

`OmarchyMenuExecutor` accepts only `menu.open` with `name=main`. Its fixed argv is
`/usr/share/omarchy/bin/omarchy menu summon root`; no shell or caller-supplied
route is accepted. Missing executable fails; timeout/nonzero is uncertain and
never retried automatically. A zero exit acknowledges the request, not verified
on-screen visibility. The live binding is opt-in, not used by runtime health.

`python3 -m ops.voice_smoke` uses a fake executor by default. Live use requires
separate human approval, `--live`, and a persistent `--journal` path. The stable
smoke command ID prevents repeat execution in that journal even across restart.
Do not change the journal path to evade that protection. Tests substitute the
subprocess call and prove exact argv, no shell, uncertainty and repeat suppression.

Current integration remains simulation-first: capture -> fake transcription ->
router -> VM policy -> fake executor -> durable events. No microphone, Whisper
process, TTS playback, keyboard binding or background service is installed. The
one separately approved menu smoke tests typed execution only, not live speech.
